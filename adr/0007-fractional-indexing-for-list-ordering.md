# ADR-0007: Fractional Indexing for List Item Ordering

**Date:** 2026-08-18
**Status:** Accepted

## Context

`LIST_ITEM` needs a user-controlled order — a user can add a venue
anywhere in a list and drag items around freely. The obvious first
approach, an integer `order` column renumbered on every insert/move, was
rejected before implementation: inserting a new item in the middle of a
1000-item list would require updating every item after the insertion
point, and a drag-and-drop reorder in a client app would need to
recompute and re-send positions for every affected row, not just the one
that moved.

The question was which of the well-known alternatives to use instead,
given the user's explicit instruction to use whatever the industry
standard actually is rather than inventing something bespoke.

## Decision

`ListItem.position` is a fractional-indexing key: a lexicographically
sortable string generated by the `fractional-indexing` PyPI package
(implementing the standard base62 fractional-indexing algorithm used by
Figma and other real-time collaborative-ordering products). Inserting,
moving, or removing an item only ever writes the one row being changed —
existing rows' positions are never renumbered. `ORDER BY position` alone
produces the correct sequence.

**Critical implementation detail: `position` must use `COLLATE "C"`, not
the database's default collation.** This was found and fixed empirically,
not assumed. An end-to-end test against the real dev database — append
three items, insert a fourth mid-list, move one to the start, remove one,
asserting exact resulting order at every step — failed on the
move-to-start case. The generated key (`"Zz"`) was correct per the
fractional-indexing algorithm's own ASCII byte-ordering rules
(`'Zz' < 'a0'` is `true` under plain byte comparison), but
`ORDER BY position` still returned it last. Root cause, confirmed by
querying `pg_database.datcollate` directly and then running
`SELECT 'Zz' < 'a0'` under it: the database's default `en_US.utf8`
collation returns `false` for that comparison — it sorts
locale-aware (case- and punctuation-sensitive rules that don't match
plain byte order), not byte-wise. The fractional-indexing algorithm's
correctness *depends on* plain byte-wise ordering; any locale-aware
collation silently breaks it. Fixed by declaring the column
`String(collation="C")` (PostgreSQL's built-in binary/byte-order
collation) — verified by re-running the exact same empirical test suite
against the corrected column, all assertions passing, and separately
confirming `information_schema.columns.collation_name = 'C'` after
migration.

## Rationale

Alternatives considered:

1. **Integer `order`, renumbered on write.** Rejected for the reasons in
   Context — O(n) writes per insert/move in the worst case, and a
   drag-and-drop client would need to batch-update many rows for a
   single-item move.
2. **Sparse integers (leave large gaps, e.g. multiples of 1000).**
   Rejected: gaps eventually run out under enough insertions in the same
   spot, at which point a renumbering pass is needed anyway — it defers
   the O(n) problem rather than solving it, and reintroduces exactly the
   kind of ad hoc scheme the user asked to avoid in favor of the real
   industry-standard approach.
3. **Fractional indexing (chosen).** No renumbering ever, arbitrarily
   many insertions between any two existing items, and a mature reference
   implementation instead of a bespoke key-generation scheme.

## Consequences

**Positive:**

- Insert, move, and remove are all single-row writes, regardless of list
  size or how many times the same spot has been inserted into.
- No renumbering pass, ever, and no batch-update requirement on the
  client for a single-item reorder.
- The library used is a maintained reference implementation of a
  well-known algorithm, not custom key-generation logic to maintain.

**Negative / trade-offs:**

- The collation requirement is a non-obvious footgun: forgetting
  `COLLATE "C"` (or a future migration accidentally dropping it) fails
  silently — no error, just wrong order — since it's a valid column that
  simply sorts differently. Documented directly in
  `app/models/list_item.py`'s own docstring, at the point of definition,
  specifically so a future change to this column doesn't rediscover the
  bug the hard way.
- `position` values grow slightly longer with repeated insertions
  squeezed into the same narrow gap (an inherent property of the
  algorithm). Not a practical concern at list sizes a single user
  curates by hand; revisit only if evidence of pathological key growth
  ever appears in production data.
