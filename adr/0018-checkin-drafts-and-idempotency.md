# ADR-0018: Check-in Drafts and Submission Idempotency

**Date:** 2026-11-12
**Status:** Accepted; implemented in `obur-backend` Phase 11

## Context

PDD §17 makes two mechanisms an MVP requirement so a check-in is never
silently lost to a bad connection: a server-synced `CHECKIN_DRAFT` before
submission, and a client-generated `idempotency_key` after it. PDD §7
already fixes the most important call, a separate draft table rather than a
`CHECKIN.is_draft` flag, so a draft can never leak into rating, badge, or
feed queries.

What the PDD left open is everything needed to actually build it: how many
drafts a user may hold, how long they live, what happens when two devices
edit the same one, how a draft becomes a check-in, what the server does when
a key is reused, and how the existing `CHECKIN` rows get a column that is
meant to be mandatory. Most of these choices are part of the API contract
`obur-web` and `obur-mobile` will be built against, so they are settled
here rather than left to the implementation.

## Decision

### Drafts

```sql
CHECKIN_DRAFT
  id              UUID PK
  user_id         UUID FK → USER ON DELETE CASCADE
  venue_id        UUID FK → VENUE NULL
  rating_taste    SMALLINT NULL
  rating_service  SMALLINT NULL
  rating_ambiance SMALLINT NULL
  rating_value    SMALLINT NULL
  note            TEXT NULL
  photo_url       VARCHAR NULL
  visibility      VARCHAR NOT NULL DEFAULT 'public'
  visited_at      DATE NULL
  visited_tz      VARCHAR NULL
  updated_at      TIMESTAMPTZ NOT NULL
  created_at      TIMESTAMPTZ NOT NULL
                                  -- INDEX (user_id, updated_at)
```

- **No limit on how many drafts a user holds.** The general rate limiter
  (ADR-0014) already bounds abuse; a per-user cap would add a rule with no
  user-facing reason.
- **A draft expires 7 days after its last edit (`updated_at`)**, not after
  creation. A draft someone is still working on must never disappear under
  them; the limit exists to clear abandoned ones.
- **Expiry is enforced at read time, cleanup is lazy.** Every draft query
  filters out rows older than the limit, so an expired draft is gone to the
  user at exactly 7 days with no job involved. Physical deletion happens
  when the owner next lists their drafts. No scheduled job is added; Phase
  14's `rarity_pct` stays the only periodic job in the system.
- **Concurrent edits from two devices: last write wins.** Each autosave
  overwrites the row and bumps `updated_at`. No version check.
- **`visibility` is stored on the draft, `NOT NULL`, defaulting to
  `public`**, the same default `CHECKIN` already has. The user can change it
  at any point, and the value travels with the draft across devices. This
  closes a gap in the PDD's original schema: without it, a `close_friends`
  choice made on a phone would be invisible on web, and a submission from
  web would quietly fall back to `public`.
- **`visited_tz` is stored on the draft and written together with
  `visited_at`.** It describes where the visit happened, not where the
  submission happens. The device that sets the date sets its own timezone
  in the same write, so a draft started at the venue and finished days later
  on a laptop in another timezone keeps the correct value.

### Submission

Drafts are served under `/api/v1/checkin-drafts`, not `/checkins/drafts`:
the latter shares a path shape with `/checkins/{checkin_id}`, and which
handler answered would then depend on router registration order.

Submission goes through the existing `POST /api/v1/checkins`, with the full
check-in payload plus an optional `draft_id`. There is no separate
"promote this draft" endpoint.

- The server creates the `CHECKIN` and deletes the draft **in the same
  transaction**.
- If the referenced draft no longer exists (expired, already submitted from
  another device, deleted), the check-in is still created. A draft's only
  purpose is resuming the flow; by the time of submission the client holds
  the complete data and the draft has done its job.
- `draft_id` is never stored on `CHECKIN`. There is no lasting link between
  a check-in and the draft it came from.

### Idempotency

Follows the IETF HTTPAPI working group's Idempotency-Key header draft
(`draft-ietf-httpapi-idempotency-key-header`), the same model Stripe's API
uses.

- The key travels in the **`Idempotency-Key` request header**, and is
  stored as `CHECKIN.idempotency_key` with `UNIQUE (user_id,
  idempotency_key)`.
- The key **must be a UUID**, generated by the client when the user taps
  Save and reused unchanged on every retry of that submission.
- The server stores a **hash of the check-in's content** alongside the key.
  `draft_id` is excluded from the hash: it is not part of the check-in.
- Responses:

| Situation | Response |
|---|---|
| Header missing | `400` |
| Header not a UUID | `400` |
| Key already used with **different** content | `422` |
| Key already used, original request still being processed | `409` |
| Key already used with the **same** content | The original response, unchanged: `201` with the original check-in |
| Key's original check-in has since been soft-deleted | `404`; nothing is recreated |

  Each error carries its own `urn:obur:problem:{slug}` type per ADR-0015, so
  a client branches on the type, not on the status alone.

- **Existing `CHECKIN` rows are backfilled** with a random UUID by the
  migration that adds the column, and the column is **`NOT NULL`**.
- **The in-progress `409` uses a transaction-scoped advisory lock** keyed
  on the user and the key. Without it, PostgreSQL's unique index would
  make a concurrent duplicate wait for the first request and then replay
  it, so `409` would never actually be returned.
- **A replay returns the check-in's current state**, not a stored copy of
  the first response. Storing responses would need its own table for no
  practical gain; the only difference arises when the check-in was edited
  between the original request and the retry.

### Row Level Security

`checkin_drafts` is owner-only for every operation. **No admin exception.**

## Rationale

**Full payload on submit, not a server-side promote.** A promote endpoint
would make the draft row the source of truth at the moment of submission.
Combined with last-write-wins and mobile's automatic retry, that can
produce a check-in different from the one the user saw: the phone queues a
retry, another device edits the draft meanwhile, the retry promotes the
edited version. A self-contained request makes a retry carry exactly what
was on screen when the user tapped Save. It also keeps a single creation
path, so validation and idempotency live in one place.

**Reject a reused key with different content instead of silently returning
the original.** A correctly written client never does this; it only
happens when a client has a bug. Silently returning the original would let
a user believe they saved one thing while another was stored, the kind of
silent failure this project has consistently chosen to make loud.

**Status codes come from the standard, not from preference.** `422` for a
mismatched payload, `409` for an in-flight duplicate, and replaying the
original response are what the IETF draft specifies; inventing a different
mapping would mean every client author has to learn an Obur-specific
convention for something the industry already agreed on.

**`404` for a soft-deleted original.** The realistic path is mobile's
retry queue: the response to the first submission is lost, the user
deletes the check-in from web, then the phone reconnects and retries with
the same key. Recreating it would undo the user's own deletion; returning
the deleted row would expose deleted content. `404` tells the client the
submission no longer exists so it can drop it from its queue.

**Backfill and `NOT NULL` instead of leaving old rows empty.** A backfilled
key does nothing functionally: no client holds it, so no retry will ever
match it. It is indistinguishable from a real key, though, and it lets the
database itself guarantee every check-in has one. With a nullable column,
"a key is required" would live only in API code, and any future code path
that forgets it would go unnoticed. This is the same reasoning behind
ADR-0016: put the guarantee where a forgotten check can't bypass it. There
is no production data, so the backfill carries no risk.

**Read-time expiry instead of a scheduled cleanup job.** A job that fails or
never runs would leave expired drafts visible; a read-time filter cannot
fail that way. Railway's Cron is also currently suspended
(`obur-backend/docs/deployment.md`).

**No admin access to drafts.** A draft is unpublished content: it cannot
be reported, never appears in a feed, and needs no moderation. It may
contain notes the user never intends to share. Granting access no workflow
needs would contradict the data-minimisation stance in PDD §17. Account
deletion still works: drafts cascade off `USER`.

### Alternatives considered

- **One active draft per user.** Rejected: a user may start check-ins for
  two visits in one evening.
- **Expiry from `created_at`.** Rejected: punishes a draft still in use.
- **Optimistic concurrency (reject stale writes via `updated_at`).**
  Rejected for now: the realistic case is one person switching devices,
  not two editing at once, and a conflict dialog is more friction than
  losing a few seconds of a superseded edit.
- **`visited_tz` taken from the submitting device.** First proposed, then
  rejected: it records where the submission happened, which is wrong for a
  draft finished in another timezone.
- **`visibility` nullable with no default, required on submit.** Rejected:
  storing the value on the draft already solves the cross-device problem,
  and requiring an explicit choice adds friction without protecting
  anything further.
- **Key in the request body.** Rejected in favour of the standard header.

## Consequences

- Clients must send `Idempotency-Key` on every check-in creation. Nothing
  breaks, since no client exists yet.
- Clients must autosave `visited_tz` together with `visited_at`, never one
  without the other.
- `CHECKIN` gains a content-hash column. The hashed field set is a defined
  list in code; adding a field to `CHECKIN` means deciding whether it joins
  that list.
- Expired drafts of users who never return stay in the table physically.
  They are invisible and small; a cleanup job can be added later if volume
  ever warrants it.
- Last write wins means an edit made seconds before another device's
  autosave can be lost. Accepted for the reasons above.
- `checkin_drafts` deviates from the owner-or-admin pattern every other
  owned table uses under ADR-0016. The deviation is intentional and stated
  in the migration.
- Phase 15 decides what `photo_url` holds before submission and whether an
  expired draft's uploaded photo must be cleaned from R2. Until then the
  field is stored as given.
